# Журнал рішень

Що обрали, чому, і що відкинули. Нове рішення — новий запис унизу.

## D-1. Читати трек через системний API «Керування мультимедіа» Windows

**Контекст.** Новий Apple Music для Windows (Microsoft Store) не має ні COM-інтерфейсу, як старий
iTunes, ні публічного API, ні файлу з історією прослуховувань.

**Рішення.** Брати дані з `Windows.Media.Control.GlobalSystemMediaTransportControlsSessionManager` —
того самого джерела, що показує плитку плеєра біля регулятора гучності. Apple Music туди пише
назву, виконавця, обкладинку, стан і таймлайн. Сесію Apple Music шукаємо за AppUserModelId
(`AppleInc.AppleMusicWin_…`), щоб не скроблити браузер, Spotify тощо. Опитуємо раз на секунду
замість підписки на події: події цього API на практиці приходять ненадійно, а опитування
дешеве й просте.

**Відкинуто.** iTunes COM — працює лише зі старим iTunes. Читання пам'яті процесу чи UI Automation
вікна Apple Music — крихке, ламається з кожним оновленням.

**Наслідки.** Підтримується лише Apple Music з Microsoft Store; потрібна Windows 10 1809+.
Позицію в треку плеєр оновлює рідко, тому ми її екстраполюємо від `LastUpdatedTime`.

## D-2. Розрізати «Виконавець — Альбом»

**Контекст.** Apple Music для Windows віддає в поле Artist рядок «Виконавець — Альбом»
(довге тире U+2014), а AlbumTitle лишає порожнім. Без обробки last.fm отримав би неіснуючого
виконавця.

**Рішення.** Якщо альбом порожній і в полі виконавця є « — », розрізаємо по першому входженню.
Якщо альбом заповнений (Apple колись виправить) — нічого не чіпаємо.

**Наслідки.** Виконавець, у чиїй назві є « — », розріжеться неправильно — свідомий компроміс,
таких майже немає.

## D-3. Правила скроблу — як у last.fm, з обліком реального часу

**Рішення.** Скробл, коли трек ≥ 30 с і реально прослухано половину або 4 хв. Рахуємо лише
секунди, коли плеєр у стані «грає», не більше 5 с за одне опитування (сон ПК не рахується
прослуханим). Невідома тривалість → чекаємо 4 хв. Повтор тієї ж пісні розпізнаємо, коли позиція
стрибає з > 30 с на < 5 с. Час скроблу — момент, коли трек почав грати.

**Відкинуто.** Рахувати за позицією в треку — перемотування вперед давало б фальшиві скробли.

## D-4. Черга скроблів на диску

**Рішення.** Кожен скробл спершу записується в `queue.json`, потім надсилається пачками до 50
(ліміт last.fm). При мережевій або тимчасовій помилці — повтор через хвилину; при недійсній
сесії — чекаємо повторного входу; пачки, які last.fm відхиляє як некоректні (коди 6, 13),
викидаємо, щоб не блокували чергу. Скробли старші 14 днів видаляємо — last.fm їх однаково не прийме.

## D-5. Вхід через auth.getMobileSession, власний API-ключ користувача

**Контекст.** Користувач хоче в налаштуваннях саме логін/пароль. last.fm вимагає API key і secret
для будь-якого застосунку, а вшитий у публічний exe secret перестає бути секретом.

**Рішення.** Користувач один раз створює свій API-ключ на last.fm (2 хвилини, інструкція в README)
і вводить логін/пароль. Через `auth.getMobileSession` отримуємо ключ сесії; пароль не зберігаємо.
API secret і ключ сесії шифруємо DPAPI (CurrentUser).

**Відкинуто.** Вбудований ключ розробника — secret витік би з exe, а last.fm може заблокувати ключ
для всіх. Вхід через браузер (auth.getToken) — зручніше для чужих людей, але потребує того самого
ключа; можна додати пізніше.

## D-6. C# / .NET 8 WPF, один self-contained exe

**Рішення.** WPF для вікон, `NotifyIcon` з WinForms для трею (у WPF свого немає). Публікуємо
self-contained single-file: один exe ~78 МБ, нічого не треба встановлювати. Збирає GitHub Actions
на `windows-latest`, exe — артефакт збірки або вкладення релізу на тег `v*`.

**Відкинуто.** Framework-dependent exe (~1 МБ) — вимагав би від користувача поставити .NET Desktop
Runtime. Python — важче зібрати в один exe, більше залежностей.

**Наслідки.** Логіку (`src/ScrobbleMe/Core`) винесено без залежностей від Windows, щоб тести йшли
на будь-якій ОС.
